# 0.11.0-beta.2：实体别名与初始化容错紧急修复

## 修复的问题

HA Core 2026.9.2 的 MCP 上下文可返回 `名称, 别名`。原程序将整段字符串视为一个名称；后续别名补全又按 friendly_name 与整串严格相等匹配，因此无法修正。存在多个同域实体时，控制请求可能在本地被拒绝为 `target_requires_clarification`，没有调用 MCP 控制后端。

本次通过完整注册表条目重建名称集合，处理表示默认计算名称的 null，并在唯一匹配时还原主名称、别名和实体 ID。按完整展示串匹配，避免直接用逗号切割名称。详情查询只针对已暴露且属于现有目录域的实体。

初始化还增加以下容错：

- 暴露范围读取、认证、快照及详情查询共用 10 秒工作预算。
- 单连接中最多等待 4 个有效详情请求，每项等待不超过 2 秒；仅一个接收循环按请求 ID 分发结果。
- 单实体删除、请求失败、异常详情或超时，不丢弃其他已成功补全的结果。
- 整体超时或断连时保留部分结果；基础读取失败时保留原始 MCP 目录并继续启动。
- 迟到回复不被用于其他请求；上层取消正常传播。关闭清理使用 1 秒 close_timeout，实际返回可能略超过工作预算。

## 改动范围

生产代码仅修改 `app/tools/ha_aliases.py`；新增两组回归测试。配置版本提升至 0.11.0-beta.2，以便已安装的商店版本收到更新。音频传输、VAD、播放队列、Qwen 协议和设备固件没有修改。

实体目录同时被控制路由、澄清、模型提示和自动工具生成使用，因此不能把“音频文件未改动”理解为所有语音交互均已验收。

## 验证证据

基于 GitHub 400f741，在真实 Core 2026.9.2 上对已开启测试灯执行幂等打开命令：

| 代码 | 默认名称 | 添加别名 | 恢复名称 |
|---|---|---|---|
| 原始发布版 | HA 返回成功 | 本地拒绝，未调用 MCP 控制 | HA 返回成功 |
| 别名修复候选 | HA 返回成功 | HA 返回成功 | HA 返回成功 |

测试结束恢复临时别名，灯保持原状态。这验证了控制链路，不代表进行了物理开关变化检测或完整语音测试。

初始化容错新增 13 项异步故障注入测试，覆盖乱序返回、30 个实体、请求窗口、删除、异常详情、迟到响应、单项/整体超时、断连、暴露边界、认证失败及取消。此前 156 项加本轮 13 项，共 169 项 smoke 测试通过。

## 尚未解决 / 尚未验证

1. **用户报告的全部失败未被唯一归因。** 日志中的多名称格式与已复现缺陷一致，但缺少完整启动目录，不能断言所有失败均由别名导致。
2. **未暴露或域不符的实体。** `No exposed entities found in domain(s): ["light"]` 需检查 Assist 暴露设置和真实域（如 switch）；该补丁不会自动修改暴露设置。
3. **自动生成工具的同名边界。** 下游仍按 friendly_name 从全体状态中筛选，而非按实体 ID。暴露与未暴露实体同名时可能扩大候选集合；本次未修复这一既有风险，别名恢复可能使该路径重新可达。别名合并本身的范围限制不能代表整个生成工具链已安全验收。
4. **特殊名称兼容。** HA 计算名称与 state friendly_name 不同，或 MCP 带引号、换行的特殊展示格式，仍可能无法匹配。
5. **模型别名提示。** 模型实体清单只列主名称，未同步列出完整别名；本地校验认识别名不代表模型的全部澄清行为已覆盖。
6. **慢环境可能只补全部分实体。** 预算耗尽后未成功的项目保留原值，仍可能无法使用别名控制；不会无限等待，也没有新增后台重试或热更新。
7. **发布验收边界。** 新增容错流程尚未完成真实 HA 重新部署、完整镜像启动及 Voice PE 音频/唤醒/打断验收；上表是容错补充前的别名修复实机对照。
